KhururuAI: Work in Flow Web app (2026)

The point of this project is access. Capable AI tools price out the people who would gain most from them, while every major provider (Groq, Cerebras, NVIDIA, Google, Mistral) gives away a free tier that goes unclaimed because claiming it means holding an API key. KhururuAI pools that free capacity into a product anyone can just open and use: no payment, no API key, no account at all for the first five turns. It runs today on my own pooled keys, roughly 2.3B tokens of budget; the version I’m working toward provisions each user’s own free tier at sign-in, so the ceiling scales with users instead of being divided among them, and extends the agents to Nepali language work: drafting, and filling out forms in Nepali.

A user writes what they want in plain language, an LLM router picks one of six specialists, and that specialist returns the finished thing: a researched answer with live citations, a slide deck, a PDF, working code, an image, or ordinary conversation. Uploaded documents are parsed, embedded and retrieved with page-accurate citations, PDF, DOCX, HWP and HWPX alike, so the formats people actually receive are not a reason to be locked out. Turns stream over SSE as typed events, so the interface names the specialist at ~1–2s and the model that is writing before the first token exists.

Staying free without falling over is the engineering problem. One OpenAI-compatible gateway fronts every provider, collapsing three vendor SDKs into a single client where “which provider” becomes “which model id”; agents are pinned to capability slots rather than vendors, so a model that runs dry is a one-line swap and an exhausted route falls back on its own.

Free access then sits behind two ceilings doing different jobs: a guest allowance that deliberately never refills, and a per-IP daily budget that stops the endpoint being farmed. Five Node services plus Redis, Qdrant and MinIO behind a React SPA, reproducible with one Docker Compose command, with the decisions recorded as ADRs.

v2, coming soon, turns the assistant into a team. Instead of one chat that returns a finished artifact, you spin up several AI teammates, each driving its own virtual PC. The human never leaves the loop: you can step into any bot’s desktop at any moment to hand it a file, clear a CAPTCHA, or type in a password or anything else that should never pass through a model, then step back out and let the agent carry on from where you left it. An early preview is live.

  • Role: Solo. Architecture, all five services, the SPA and deployment.
  • Tools: Node.js, Express, LangGraph.js, React, TypeScript, MongoDB, Redis, Qdrant, MinIO/S3, Docker Compose, nginx, Firebase Auth, Tavily
  • ML/Algorithms: LLM intent routing across an agent roster; multi-provider model routing with exhaustion fallback; document RAG (page-aware chunking, Gemini embeddings, score-floored retrieval under a hard context budget, validated citations)
  • Links: khururu.com · v2 preview: sangi.khururu.com

Charak: Medical Research Assistant Web appMCP server (2026)

For deterministic work, a tool-calling agent beats code-gen or one big prompt. Charak answers natural-language clinical questions from live PubMed literature and ClinicalTrials.gov v2 records, and charts the answer when the question is really about a distribution. The LLM owns language and control flow only, orchestrating typed Python tools, and never sees or writes a number. State stays server-side and it passes only opaque dataset handles, so it cannot emit a wrong figure because it is never handed one. Chart-type selection is deterministic rules; the “no matching trials” reply is code-gated rather than left to judgment. That costs more round-trips, but each is a short tool call instead of a wall of records pushed through context — cheaper per query and structurally correct.

The backend renders nothing: it returns a small flat JSON spec that Vega-Lite draws on the client, thin enough that one response feeds the chat UI, the POST /visualize API and a standalone MCP server unchanged.

The hard part was the public API, not the model. I verified every capability with live curl first, which caught the wrong assumptions. The obvious filters (filter.phase, filter.country) don’t exist; real narrowing is Essie, AREA[Phase]PHASE3. And the one aggregation endpoint can’t be scoped to a query and returns no trial IDs, so it can’t back citations either.

With no server-side aggregation, counts are resolved in tiers: exact from the full corpus, exact via a cheap per-bucket countTotal query when it’s too large to fetch, sampled-but-flagged only for unbounded fields. Because aggregation walks records instead of asking for a summary, every bar carries the trial IDs that built it.

  • Role: Solo. API research, agent and tool design, backend and frontend.
  • Tools: Python, FastAPI, Pydantic v2, MCP (Model Context Protocol), Vega-Lite, vis-network, Server-Sent Events, Docker Compose, Caddy, pytest, uv
  • ML/Algorithms: Tool-calling agent loop with server-side state handles (no numeric values in context); three-tier exact-count resolution over a non-aggregating API; deterministic data-shape → chart-type selection; entity-normalized co-occurrence network construction; LLM access through the same OpenAI-compatible gateway as KhururuAI, so it runs on pooled free-tier
  • Links: charak.khururu.com · GitHub

Bintech International Web app (2026)

Built to survive being handed over. Bintech is a B2B hardware supplier in Nepal, and I built all of it: site, CRM, assistant, server. Nobody there writes code, so the design is only correct if a salesperson can add a product, publish it and answer a customer without me. So the catalogue lives in Payload CMS 3 on Postgres: staff add and publish products from a browser admin panel, with the field labels written for a salesperson rather than for me. Who can see what is enforced inside the database query rather than filtered out in code afterwards, so an unpublished draft is never fetched for a visitor at all. Inquiries work the opposite way: anyone can submit one, nobody outside the company can read them, and staff can read but not edit what the customer wrote. The only editable field is the status, New → Contacted → Closed.

The site is built to keep working when its dependencies don’t: every catalogue query falls back to a built-in list of products, so a Postgres outage degrades to that list instead of a blank page, and inquiry emails are sent only after the lead is saved to the database, so a mail outage costs a notification, never a lead. It self-hosts on one VPS via Docker Compose behind Caddy, deployed over SSH by a GitHub Actions job that holds no repo permissions and can run only one fixed deploy command on the server.

The assistant is deliberately the predictable kind: grounded, not fine-tuned, and always in sync with the live catalogue. Each request flattens that catalogue into one compact line per product behind a 60s cache and pins it into a system prompt that forbids inventing prices and hard-codes the only two legal URL shapes (LLMs cheerfully guess /products/monitors, which 404s). So a price edit in the CRM reaches the bot’s answers within a cache window, and it cannot quote a number that isn’t in the database.

  • Role: Solo. Site, CRM, assistant, VPS, domain, DNS and mailboxes.
  • Tools: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4, Payload CMS 3, PostgreSQL 17, Drizzle migrations, Nodemailer/SMTP, sharp, Motion, Docker Compose, Caddy, GitHub Actions
  • ML/Algorithms: Catalogue-grounded LLM assistant. Live DB → compact token-efficient context behind a TTL cache, guardrailed system prompt (no invented prices/specs, closed link vocabulary, out-of-scope hand-off), SSE → plain-text delta re-emission
  • Links: bintechint.com

AirConnect: Proximity-Based Social Discovery Mobile app (2025)

Ultra-Wideband was the bet, and the hardware wasn’t ready. A friend and I wanted to start a company, and this was my idea. You are on a subway and the person across from you is reading a book you love. You want to say something, but the only options are walking up to a stranger or saying nothing, so you say nothing. AirConnect made the first move small: ping the one person in your line of sight, and let them ignore it if they want.

That premise needs direction, not distance. UWB is the only widely shipped radio that gives angle of arrival rather than just range, and “that person, over there” is an angle problem. Bluetooth knows someone is nearby, never which one. The UWB SDKs proved too unstable to build on, and without direction the premise was gone. We pivoted to GPS-based nearby discovery, which put us in dating-app territory, where Apple now rejects new entrants that aren’t meaningfully differentiated. So we stopped. Two people, six weeks: a working real-time app, and a clear answer to why the idea doesn’t survive current hardware and platform policy.

An Expo/React Native client and a Node + Socket.IO backend: nearby discovery, matching, chat, and live location sharing on a map, with Redis as the primary datastore. My friend built the Expo foundation and owned the map/GPS and chat features. I owned the backend and infrastructure: Docker/Compose, identity and access management (IAM), a PostgreSQL migration path alongside Redis, and the welcome/signup/onboarding flow, plus debugging help on the map (marker-flicker fix and compass heading).

  • Role: Two-person team. I owned the backend, infrastructure and IAM; my friend owned the map/GPS and chat.
  • Tools: Expo, React Native, TypeScript, Node.js, Express, Socket.IO, Redis, PostgreSQL, Docker Compose, cloudflared

B-Assist (Better-Assistant) Desktop app (2024)

The assistant should come to your text, not your text to the assistant. Every AI writing tool I used meant the same round-trip: leave the editor, paste into ChatGPT, read the answer, copy it back, paste again. B-Assist collapses that to a keystroke. Select text anywhere (an email, a Word document, an IDE), press ctrl+shift+X (cmd+shift+X on macOS), pick an action, and the processed text replaces your selection in place. You never leave the window you were writing in.

Working in every editor rules out integrating with any of them, so it sits under the apps rather than inside them: a global hotkey opens a small window, and robotJS drives the OS clipboard and keystrokes to lift the selection and type the result back — the same path whether the target is Gmail, Word or VS Code, with no per-app plugin to write or maintain. Models run locally through Ollama, which does two jobs at once: there is no API key to hand a non-technical user, and drafts being rewritten never leave the machine. It ships as a one-click executable for Windows and macOS, with grammar and spelling correction and English→Korean translation as the actions implemented.

Any local model works; the recommended default is Qwen3.5-4B, small enough to run on an ordinary laptop. The same idea later became a shipped product at the startup I work at, SamuGen Plugin.

  • Role: Solo.
  • Tools: ElectronJS, ReactJS, robotJS, Ollama
  • Links: GitHub · Demo · SamuGen Plugin

ReNameify: Content-Aware PDF Batch Renamer Desktop app (2024)

Written for one real user, not a spec. My sister was renaming exported PDFs by hand (opening each one, reading the header, retyping it), so she talked with me, and I watched the actual workflow, and shipped a one-click Windows installer that does it in a folder-at-a-time pass. It extracts each PDF’s text, then scores lines with a header-detection heuristic that rejects the things that look like titles but aren’t: page numbers (page 12, - 12 -), sentences ending in a full stop, lines that are mostly punctuation, and anything outside a defined length range.

Trust mattered more than accuracy here. Nothing is renamed in place. Originals stay untouched and copies land in a renamed_files/ subfolder, a PDF that fails to parse (scanned pages, no text layer) keeps its original name instead of erroring the batch, and a first-run guided tour walks a non-technical user through the three buttons. It survived contact with its one user, which is the only test that counted.

  • Role: Solo.
  • Tools: ElectronJS, Node.js, pdf-parse, fs-extra, Shepherd.js, Winston, electron-builder (NSIS one-click installer)
  • ML/Algorithms: Rule-based header extraction from first-page text: length banding, terminal-punctuation and page-number rejection, special-character-ratio filtering with a Hangul-safe character class, document-specific anchor matching, and filename sanitization with graceful fallback to the original name
  • Links: GitHub

FastRAG: Self-Hosted Document RAG Backend (2024)

No API key, no data leaving the machine. FastRAG is a document Q&A backend that comes up with a single docker compose up: a FastAPI parse/chat service, Qdrant for vectors, a CUDA llama.cpp server running a quantized Llama-3.2-3B, and a Gradio demo UI.

Ingestion offers two paths: a custom PyMuPDF reader with tunable chunk size and stride, plus an optional bridging pass that stitches the tail of one page to the head of the next so an answer split across a page break is still retrievable as one chunk; or layout-aware Markdown chunking for documents where structure carries the meaning.

Retrieval is bge-m3 dense search with a score floor, and the prompt is written to refuse rather than improvise when the retrieved references don’t cover the question. Follow-ups can be rewritten into standalone queries against conversation history kept in Qdrant, and answers stream token-by-token from llama.cpp through FastAPI to the UI, with per-response latency logged and shown to the user.

  • Role: Solo.
  • Tools: Python, FastAPI, Qdrant, llama.cpp (CUDA server), LlamaIndex, PyMuPDF/pymupdf4llm, LangChain text-splitters, Gradio, Docker Compose, Poetry, pre-commit
  • ML/Algorithms: BAAI/bge-m3 dense embeddings with cosine search and a score threshold; on-disk vectors and memmap-tuned Qdrant collections for low-RAM hosts; page-boundary overlap chunking vs. layout-aware Markdown chunking; history-conditioned query rewriting; grounded-answer prompt with an explicit refusal path
  • Links: GitHub

Probabilistic Multiview Object-Pose Estimation (2023)

One fused pose distribution per object, rather than a best-view pick. Single-view estimators disagree with each other, and choosing between them throws information away. We associated multiple estimation results with scene graphs, combined the pose distributions coming out of single-view estimators, and constructed a unified scene graph by predicting one pose distribution per object. On table-top object-pose scenarios the approach beat three baseline methods on both position and orientation accuracy.

  • Role: Neural architecture research for pose estimation and scene graph generation, then training and combined efficient inference. My teammate handled environment setup, simulation dataset creation, and visualization.
  • Links: Draft paper

6D Pose Estimation and Scene Graph Generation (2023)

Two heavy frameworks in one pipeline, and the cost shows up as framerate. I combined the Cosypose framework for 6D pose with Neural-Motif for scene graph generation and ran experiments on custom cup datasets, a single-camera setup producing both 6D pose and a dynamic scene graph. For 6 cups, with pose estimation plus relationship and attribute predictions, the combined framework ran at 1.25 frames/s.

  • ML/Algorithms: Cosypose: CNN with geometric optimization (ICP registration and non-linear optimization via Levenberg-Marquardt); Neural-Motif: Region Proposal Network with bi-directional LSTM

MBTI Prediction (2023)

One classifier pair per MBTI axis, not one model for all sixteen types. Submitted to the Qualcomm-KAIST Innovation Awards Hackathon in May 2023, predicting MBTI (a widely used personality assessment) from text. The model is a hierarchical classifier: 4 fine-tuned KoBERT classifiers and 4 SVM classifiers, one pair per section of the MBTI test.

For robustness I augmented the data by paraphrasing long answers with google-t5-base, and ran EDA on the question information to extract a new feature set from the questions themselves. Fine-tuning KoBERT meant adding a fully connected layer with softmax activation at the end, then adaptively fine-tuning by varying the amount of layer-freezing in two steps.

I placed 3rd on the Phase-2 private leaderboard. The slides cover the results, the other approaches I tried, and future work.

  • ML/Algorithms: KoBERT fine-tuning, SVM, hierarchical classification, paraphrase-based data augmentation
  • Links: Presentation

Movie Recommendation (Netflix Prize style)

Given <USER ID>, <MOVIE ID>, <TIMESTAMP> rows, I filled the missing <RATING> column by factorizing the sparse user-movie utility matrix as R ≈ UVᵀ and training both factors with Alternating Least Squares against RMSE. Two-fold normalization first (user mean, then movie mean), then denormalize to predict.

  • Tools: NumPy, Python
  • ML/Algorithms: Dimensionality reduction (UV-decomposition), Alternating Least Squares
